# ADR 0002 — Transactional Outbox para publicação confiável de eventos

**Status:** Proposto
**Data:** 2026-11-24
**Relacionada a:** ADR 0001 (RabbitMQ para processamento assíncrono)

## Contexto

Na ADR 0001, a API persiste a candidatura como `RECEBIDA` e depois publica `SolicitacaoCompetenciasEvento` no RabbitMQ. São duas operações em sistemas diferentes (PostgreSQL e RabbitMQ) que não compartilham transação. Se a API cair ou o broker ficar indisponível entre as duas, a candidatura fica gravada, mas o evento nunca é publicado, e ela permanece presa em `RECEBIDA` indefinidamente.

## Decisão

Adotar o padrão **Transactional Outbox**:

1. Na mesma transação SQL que salva a `Candidatura`, a API grava o evento em uma tabela `outbox_eventos` (`eventId`, `tipo`, `payload`, `publicadoEm`).
2. Um processo *relay* lê periodicamente os eventos não publicados e os envia ao RabbitMQ.
3. Após a confirmação do broker (publisher confirms), o relay marca `publicadoEm`.

A entrega passa a ser *at-least-once*. Por isso os consumidores continuam idempotentes, usando `eventId` e o estado atual da candidatura, conforme a ADR 0001.

## Consequências

### Vantagens
- Não há perda de evento por falha entre a persistência e a publicação.
- A resposta `202 Accepted` só é dada após o registro atômico do evento.
- Preserva o desacoplamento da ADR 0001.

### Débitos e riscos aceitos
- Nova tabela e novo processo (relay) para operar e monitorar.
- Latência adicional pequena entre o commit e a publicação.
- Possibilidade de publicação duplicada, tratada pela idempotência dos consumidores.

## Alternativas consideradas
- **Publicar direto após o commit (atual):** simples, mas com janela de perda de evento.
- **Two-Phase Commit (2PC):** garante atomicidade, mas o RabbitMQ não o suporta de forma prática e adiciona acoplamento.
